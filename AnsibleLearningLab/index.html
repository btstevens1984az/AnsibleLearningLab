Welcome to Ansible

Your complete ground-up guide. Ansible is an agentless IT automation tool that uses SSH (Linux) or WinRM (Windows) to configure systems, deploy apps, and orchestrate workflows — all from simple YAML files.

What Ansible Does

Configuration Management

Enforce desired state on servers — packages, services, files, users.

Application Deployment

Deploy code, restart services, run migrations in a repeatable way.

Orchestration

Coordinate multi-step workflows across many hosts in order.

Key Principle — Idempotency Ansible tasks should be safe to run repeatedly. If a web server is already installed and configured correctly, re-running the playbook should report ok (no change), not break anything. This is the foundation of reliable automation.

Core Terminology

TermDefinition
Control NodeThe machine where Ansible is installed and from which you run commands (your laptop, a CI runner, or Ansible Controller).
Managed Node / HostAny machine Ansible configures remotely. No Ansible agent required on managed nodes.
InventoryThe list of hosts and groups Ansible targets.
PlaybookA YAML file defining automation workflows (plays → tasks).
ModuleA unit of work Ansible executes (e.g., copy, yum, service).
TaskA single module invocation inside a playbook.
RoleA reusable bundle of tasks, templates, variables, and handlers.
FactDiscovered information about a host (OS, IP, memory) gathered automatically.

Recommended Learning Path

  1. Architecture & Install — Understand agentless SSH/WinRM and set up your control node.
  2. Inventory & Ad-Hoc — Target hosts and run one-off commands before writing playbooks.
  3. Playbooks → Tasks → Variables — Build real automation in YAML.
  4. Templates, Handlers, Roles — Structure reusable, production-grade content.
  5. Vault & Collections — Secure secrets and use community/vendor modules.
  6. Controller / AWX — Scale with RBAC, scheduling, and job templates.

Architecture

Ansible is agentless. The control node pushes modules over the network; managed nodes execute them and return JSON results.

┌─────────────────────────────────────────────────────────────────┐ │ ANSIBLE CONTROL NODE │ │ (your laptop · CI/CD · Ansible Automation Platform / Controller) │ │ │ │ ansible-playbook site.yml ──► Inventory + Playbooks/Roles │ └───────────────────────────────┬───────────────────────────────────┘ │ ┌───────────────────┼───────────────────┐ │ SSH (port 22) │ WinRM (5985/5986) │ ▼ ▼ ▼ ┌────────────┐ ┌────────────┐ ┌────────────┐ │ Linux Host │ │ Linux Host │ │ Windows │ │ (managed) │ │ (managed) │ │ (managed) │ │ No agent! │ │ No agent! │ │ No agent! │ └────────────┘ └────────────┘ └────────────┘

How a Task Runs

  1. Ansible connects to the host via SSH/WinRM.
  2. It copies a Python module (or PowerShell script on Windows) to a temp directory.
  3. The module executes locally on the managed node.
  4. Results (changed/ok/failed + output) return as JSON to the control node.
  5. Temp files are cleaned up.

Installation & Setup

Install Ansible on a control node only. Never install the full Ansible package on managed nodes.

Install ansible-core (Recommended)

# macOS (Homebrew)
brew install ansible

# RHEL / Fedora
sudo dnf install ansible-core

# Ubuntu / Debian
sudo apt update && sudo apt install ansible

# Python pip (any OS — use a venv)
python3 -m venv ~/ansible-venv
source ~/ansible-venv/bin/activate
pip install ansible-core ansible-lint

Verify Installation

ansible --version
ansible-doc -l | head          # list available modules
ansible localhost -m ping      # test against yourself

Configure ansible.cfg

Place in project root, ~/.ansible.cfg, or /etc/ansible/ansible.cfg. Project-level config is best for teams.

ansible.cfg 
[defaults]
inventory = inventories/production/hosts.yml
remote_user = ansible
private_key_file = ~/.ssh/ansible_deploy_key
host_key_checking = False          # True in production with known_hosts
retry_files_enabled = False
stdout_callback = yaml               # or ansible.builtin.default
interpreter_python = auto_silent
gathering = smart
fact_caching = jsonfile
fact_caching_connection = /tmp/ansible_facts
fact_caching_timeout = 86400

[privilege_escalation]
become = True
become_method = sudo
become_user = root
become_ask_pass = False

[ssh_connection]
pipelining = True
ssh_args = -o ControlMaster=auto -o ControlPersist=60s

SSH Key Setup for Linux Targets

# On control node — generate a dedicated deploy key
ssh-keygen -t ed25519 -f ~/.ssh/ansible_deploy_key -C "ansible-control"

# Copy public key to managed node (or use ssh-copy-id)
ssh-copy-id -i ~/.ssh/ansible_deploy_key.pub ansible@web01.example.com

# On managed node — grant passwordless sudo to ansible user
# /etc/sudoers.d/ansible:
ansible ALL=(ALL) NOPASSWD: ALL
Windows WinRM Setup Windows hosts require WinRM configured with HTTPS (5986) and a certificate. Use the ansible.windows collection. See the Windows Setup Guide for the full bootstrap process including ConfigureRemotingForAnsible.ps1.

Inventory

The inventory defines which hosts Ansible manages, organized into groups with variables attached at every level.

INI Format (Classic)

inventories/production/hosts.ini 
[webservers]
web01.example.com ansible_host=10.0.1.10
web02.example.com ansible_host=10.0.1.11

[dbservers]
db01.example.com ansible_host=10.0.2.10

[linux:children]
webservers
dbservers

[production:children]
linux

[webservers:vars]
ansible_user=ansible
nginx_worker_processes=4

YAML Format (Recommended)

inventories/production/hosts.yml 
all:
  children:
    production:
      children:
        webservers:
          hosts:
            web01.example.com:
              ansible_host: 10.0.1.10
            web02.example.com:
              ansible_host: 10.0.1.11
        dbservers:
          hosts:
            db01.example.com:
              ansible_host: 10.0.2.10
      vars:
        ansible_user: ansible
        env: production

Ad-Hoc Commands

One-off commands for quick tasks, troubleshooting, and learning modules before committing to playbooks.

Syntax

ansible <pattern> -m <module> -a "<module_args>" [options]

Essential Ad-Hoc Examples

# Ping all hosts in inventory
ansible all -m ping

# Run a shell command on webservers group
ansible webservers -m ansible.builtin.command -a "uptime"

# Install package (become root)
ansible webservers -m ansible.builtin.dnf -a "name=nginx state=present" -b

# Copy a file
ansible webservers -m ansible.builtin.copy -a "src=./index.html dest=/var/www/html/ owner=nginx" -b

# Gather facts and print hostname
ansible web01.example.com -m ansible.builtin.setup -a "filter=ansible_hostname"

# Reboot hosts (with 300s timeout)
ansible all -m ansible.builtin.reboot -a "reboot_timeout=300" -b

# Limit to one host, check mode (dry run)
ansible webservers -m ansible.builtin.dnf -a "name=nginx state=present" -b --limit web01 --check

Playbooks

Playbooks are YAML files that define ordered automation. A playbook contains one or more plays; each play targets a host group and runs a list of tasks.

playbook.yml └── play (targets: webservers, become: true) ├── task 1: install nginx ├── task 2: copy config template ├── task 3: enable service └── handler: restart nginx (notified by task 2)

Minimal Playbook

site.yml 
---
- name: Configure web servers
  hosts: webservers
  become: true
  gather_facts: true

  vars:
    nginx_port: 80

  tasks:
    - name: Ensure nginx is installed
      ansible.builtin.package:
        name: nginx
        state: present

    - name: Ensure nginx is running and enabled
      ansible.builtin.service:
        name: nginx
        state: started
        enabled: true

Running Playbooks

ansible-playbook site.yml
ansible-playbook site.yml --limit web01.example.com
ansible-playbook site.yml --tags nginx --skip-tags backup
ansible-playbook site.yml --check --diff          # dry run with diffs
ansible-playbook site.yml -e "nginx_port=8080"    # extra vars
ansible-playbook site.yml --start-at-task "Ensure nginx is installed"

Playbook with Roles

site.yml (production pattern) 
---
- name: Apply common baseline to all hosts
  hosts: all
  become: true
  roles:
    - common

- name: Configure web tier
  hosts: webservers
  become: true
  roles:
    - nginx
  vars:
    nginx_worker_processes: 4
YAML Rules Use spaces not tabs. Start files with ---. Quote strings containing colons. Task names are mandatory in production — they appear in logs and Controller job output.

Task Anatomy

- name: Create application directory    # Human-readable (required)
  ansible.builtin.file:                    # FQCN module name
    path: /opt/myapp
    state: directory
    owner: appuser
    group: appuser
    mode: '0755'
  tags: [app, directories]
  when: deploy_app | bool
  register: app_dir_result
  notify: Restart application

command vs shell vs raw

command — No shell features (no pipes, redirects). Safer default.

- ansible.builtin.command:
    cmd: /usr/bin/uptime

shell — Full shell. Use when you need pipes or redirects.

- ansible.builtin.shell:
    cmd: "cat /var/log/app.log | grep ERROR"
Prefer modules Instead of shell: yum install nginx, use dnf: name=nginx state=present. The module knows if nginx is already installed.

changed_when & failed_when

- name: Run health check script
  ansible.builtin.command: /opt/scripts/healthcheck.sh
  register: health_result
  changed_when: false           # read-only command, never "changed"
  failed_when: health_result.rc != 0

- name: Run migration (only changed if output contains MIGRATED)
  ansible.builtin.command: /opt/app/migrate.sh
  register: migrate_result
  changed_when: "'MIGRATED' in migrate_result.stdout"

Blocks — Error Handling

- name: Deploy with rollback on failure
  block:
    - name: Copy new release
      ansible.builtin.copy:
        src: releases/v2/
        dest: /opt/app/
    - name: Run smoke test
      ansible.builtin.uri:
        url: http://localhost/health
        status_code: 200
  rescue:
    - name: Rollback to previous release
      ansible.builtin.command: /opt/scripts/rollback.sh
  always:
    - name: Log deployment attempt
      ansible.builtin.lineinfile:
        path: /var/log/deployments.log
        line: "{{ ansible_date_time.iso8601 }} deploy on {{ inventory_hostname }}"

Variables & Facts

Variables parameterize your automation. Facts are auto-discovered variables about each host.

Defining Variables

# group_vars/webservers/main.yml
nginx_port: 80
nginx_worker_processes: "{{ ansible_processor_vcpus | default(2) }}"
app_version: "2.4.1"

# host_vars/web01.example.com/main.yml
nginx_worker_processes: 8   # overrides group var for this host

# In playbook
vars:
  deploy_env: production

# Command line (highest precedence)
ansible-playbook site.yml -e "app_version=2.5.0"

Jinja2 Templating

{{ variable }}                    # output value
{{ variable | default('fallback') }}  # with default
{{ list | join(',') }}              # filter
{% if env == 'production' %}...{% endif %}  # conditionals
{% for host in groups['webservers'] %}...{% endfor %}  # loops

# Useful filters for automation engineers
{{ my_var | b64encode }}
{{ vault_password | password_hash('sha512') }}
{{ config_file | basename }}
{{ ip_list | select('match', '^10\\.') | list }}

register & set_fact

- name: Check disk space
  ansible.builtin.command: df -h /
  register: disk_check

- name: Show disk output
  ansible.builtin.debug:
    msg: "{{ disk_check.stdout }}"

- name: Set computed variable for later tasks
  ansible.builtin.set_fact:
    needs_cleanup: "{{ disk_check.stdout is search('[8-9][0-9]%') }}"
    cacheable: true   # persist in fact cache

Templates & Handlers

Templates render Jinja2 files on the control node and push the result to managed nodes. Handlers restart services only when notified by a changed task.

Template Example

roles/nginx/templates/nginx.conf.j2 
user nginx;
worker_processes {{ nginx_worker_processes }};
error_log /var/log/nginx/error.log;

events {
    worker_connections {{ nginx_worker_connections | default(1024) }};
}

http {
    server {
        listen {{ nginx_port }};
        server_name {{ ansible_fqdn }};
        root /var/www/html;
    }
}
Task using template 
- name: Deploy nginx configuration
  ansible.builtin.template:
    src: nginx.conf.j2
    dest: /etc/nginx/nginx.conf
    owner: root
    group: root
    mode: '0644'
    validate: nginx -t -c %s   # test before applying
  notify: Restart nginx

Handlers

Handlers run at the end of the play, only once, and only if notified. Multiple tasks can notify the same handler — it runs once.

roles/nginx/handlers/main.yml 
---
- name: Restart nginx
  ansible.builtin.service:
    name: nginx
    state: restarted

- name: Reload nginx
  ansible.builtin.service:
    name: nginx
    state: reloaded
listen — Handler Chains Handlers can listen: "refresh web services" and tasks can notify: "refresh web services" to trigger multiple handlers with one notification.

Loops & Conditionals

Control flow in Ansible uses Jinja2 expressions — no traditional programming loops outside of Jinja.

when — Conditionals

- name: Install nginx on RedHat family
  ansible.builtin.dnf:
    name: nginx
    state: present
  when: ansible_os_family == 'RedHat'

- name: Install nginx on Debian family
  ansible.builtin.apt:
    name: nginx
    state: present
  when: ansible_os_family == 'Debian'

loop — Iterate Lists

- name: Ensure required packages are installed
  ansible.builtin.package:
    name: "{{ item }}"
    state: present
  loop:
    - vim
    - htop
    - curl
    - git

- name: Create application users
  ansible.builtin.user:
    name: "{{ item.name }}"
    groups: "{{ item.groups }}"
    shell: /bin/bash
  loop:
    - { name: 'appuser', groups: 'wheel' }
    - { name: 'deploy', groups: 'docker' }

loop vs with_* (Legacy)

Modern Ansible uses loop. Legacy forms like with_items, with_dict still work but prefer loop + filters.

# Loop over dictionary
- name: Set sysctl values
  ansible.posix.sysctl:
    name: "{{ item.key }}"
    value: "{{ item.value }}"
  loop: "{{ sysctl_settings | dict2items }}"

Roles

Roles package related tasks, defaults, vars, templates, handlers, and files into a reusable unit — the standard way to organize production Ansible.

roles/nginx/ ├── defaults/ # lowest precedence vars (overridable) │ └── main.yml ├── vars/ # role-internal vars (higher precedence) │ └── main.yml ├── tasks/ │ └── main.yml # entry point ├── handlers/ │ └── main.yml ├── templates/ │ └── nginx.conf.j2 ├── files/ # static files for copy module ├── meta/ │ └── main.yml # role dependencies └── README.md

Creating a Role

ansible-galaxy role init nginx
ansible-galaxy role init common --init-path roles/

Role Dependencies (meta/main.yml)

# roles/nginx/meta/main.yml
dependencies:
  - role: common
  - role: firewall
    vars:
      open_ports:
        - 80
        - 443

Ansible Vault

Encrypt sensitive data (passwords, API keys, certificates) at rest in your Git repository.

Vault Commands

# Create encrypted file
ansible-vault create group_vars/all/vault.yml

# Encrypt existing file
ansible-vault encrypt group_vars/all/secrets.yml

# Edit encrypted file in place
ansible-vault edit group_vars/all/vault.yml

# Run playbook with vault
ansible-playbook site.yml --ask-vault-pass
ansible-playbook site.yml --vault-password-file ~/.vault_pass

# Encrypt a single string
ansible-vault encrypt_string 'SuperSecretP@ss' --name 'db_password'

Using Vault Variables

group_vars/all/vault.yml (encrypted) 
vault_db_password: SuperSecretP@ss
vault_api_token: abc123xyz
group_vars/all/main.yml (plain text references) 
# Never put secrets in plain text — reference vault_* vars
db_password: "{{ vault_db_password }}"
api_token: "{{ vault_api_token }}"
Controller Integration In Ansible Automation Platform, store vault credentials as Credential Types → Vault and attach them to Job Templates. Never commit .vault_pass files to Git.

Ansible Automation Platform / Controller

Scale Ansible beyond CLI — RBAC, scheduling, credential injection, job templates, workflows, and audit logging. Controller is the supported enterprise product (AWX is the upstream open-source project).

Developer pushes to Git │ ▼ ┌──────────────────┐ ┌─────────────────────┐ │ Project (Git) │────►│ Job Template │ │ playbooks repo │ │ - Inventory │ └──────────────────┘ │ - Playbook │ │ - Credentials │ │ - Execution Env │ └──────────┬──────────────┘ │ Manual run / Schedule / Webhook / Workflow │ ▼ Managed Hosts (via SSH/WinRM)

Controller Core Objects

ObjectCLI EquivalentDescription
Organization—Top-level tenant / business unit
Inventory-iHosts and groups (can sync from cloud)
Projectplaybook pathGit repo containing playbooks/roles
Credential--vault-pass, SSH keysMachine, cloud, vault, SCM credentials

Typical Controller Workflow Setup

  1. Create Organization — e.g., "Infrastructure Team"
  2. Add Credential — Machine credential (SSH key) + Vault credential + SCM (Git token)
  3. Create Project — Point to Git repo, set update on launch
  4. Create Inventory — Static, constructed, or sourced from VMware/AWS
  5. Create Execution Environment — Custom EE image with your collections
  6. Create Job Template — Bind inventory + project + playbook + credentials + EE
  7. Assign RBAC — Teams get execute/admin on job templates
  8. Run or Schedule — Manual launch, cron schedule, or survey prompts

Job Template Survey (Extra Variables)

Surveys prompt operators at launch time — useful for patch windows, target environments, or maintenance modes.

# Survey variable: patch_category (multiple choice: security, bugfix, all)
# Survey variable: reboot_after (boolean)
# Passed to playbook as extra vars automatically

- name: Apply patches
  ansible.builtin.dnf:
    name: "*"
    state: latest
    security: "{{ patch_category == 'security' }}"
  when: patch_category != 'none'

Best Practices

Patterns used by mature automation teams — apply these from day one.

Project Structure

  • One Git repo per domain (web, db, windows, network)
  • inventories/ per environment (dev/staging/prod)
  • Never put secrets in plain text — use Vault
  • Pin collection versions in requirements.yml
  • Use FQCN for all modules (ansible.builtin.copy)

Task Writing

  • Every task needs a descriptive name:
  • Prefer modules over shell/command
  • Use tags for partial runs (--tags)
  • Use --check --diff before production runs
  • Set changed_when: false on read-only commands

Operations

  • Test in dev inventory first, then staging, then prod
  • Use serial: or max_fail_percentage for rolling updates
  • Enable fact caching for large inventories
  • Log to Controller — avoid running ad-hoc in prod from laptops
  • Document survey vars and extra vars in role READMEs

Security

  • Dedicated service account per environment
  • Least-privilege sudo (not NOPASSWD: ALL in prod)
  • Rotate vault passwords via Controller credentials
  • Sign commits, protect main branch, require PR reviews
  • Scan with ansible-lint and ansible-test

Rolling Updates

- name: Rolling web server update
  hosts: webservers
  serial: "25%"          # or serial: 1 for one-at-a-time
  max_fail_percentage: 0
  order: sorted            # alphabetical; or reverse_sorted, shuffle
  tasks:
    ...
